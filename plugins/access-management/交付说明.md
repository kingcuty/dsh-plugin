## 一、这个功能解决什么问题

浏览器认证原先只有一个**进程级启动令牌**（`dsh web` 启动时打印的 `?token=...` 登录链接），所有浏览器共用：
没法给单台设备单独发凭据，看不到有哪些设备登录着，也没法只踢掉其中一台（只能重启进程，把所有人一起踢下线）。

本功能给 DSH 的 `connection` 加了一个持久化的**访问目录**，并在设置页里新增 **访问** 分区：

- **登录令牌**：填写设备名 → 新建令牌 → 页面给出**一次性登录链接**（`https://<你的域名>/?token=<secret>`）；
  在目标设备打开该链接即换取 30 天会话 cookie，该设备随即出现在设备列表里。令牌 secret 只在签发这一次的返回值里出现，其它视图一律脱敏。
- **设备列表**：记录每台设备的签发令牌、浏览器与地址、首次出现 / 最近活跃 / 到期时间；支持**重命名**与**登出**（登出后该设备下一次请求返回 401）。
- **吊销**：吊销某个令牌会连带吊销它签发的所有设备。
- **恢复入口**：进程启动令牌不放进访问目录，认证时优先匹配它——目录文件损坏时仍能用它进设置页修复；目录损坏会**暂停吊销生效并在页面提示**，而不是把所有人锁在门外。
- **权限模型**：任何已登录的设备都能管理令牌（进入该页面本身就需要会话 cookie，这就是部署现有的授权模型）。
- **落盘位置**：令牌与设备存在 DSH credential store 的 `client-connection/browser-access` 记录中（**明文**，与其它凭据同一信任级别）。

```
│   ├── 0002-refuse-pre-directory-session-cookies.patch        拒绝升级前的旧会话 cookie
│   └── 0003-persist-settings-document-off-loopback.patch      非 loopback 浏览器也用持久化设置
└── overlay/             38 个受影响文件的完整副本（补丁打不上时的兜底，按仓库相对路径摆放）
```

三个补丁的取舍说明：

- **0001** 是功能本体：`packages/client/connection` 新增访问目录与 Host 侧 `browserAccess` Remote 命名空间、改造浏览器认证；新增客户端插件包 `packages/client/ui-settings-access`；在 web-app 名册与 `tsconfig` 聚合里注册；同步 `pnpm-lock.yaml`。
- **0002** 让吊销不可绕过：升级前签发的 v1 cookie 不带设备 id，访问目录既列不出也吊销不了，因此一律拒绝。
- **0003** 是局域网/域名部署需要的：上游默认「非 loopback 浏览器把设置文档降级到内存后端」，本补丁固定为 `host` 持久化。**loopback 部署行为完全不变**，只在本机使用的话装不装都一样，默认装在包里。

## 三、前置条件

1. 目标机是 deepseek-harness 的 **git 源码检出**，并且能正常构建（`pnpm install` + `pnpm run build` 跑得通）。
2. 版本基线 `0.1.5-rc.2`（`c291e79` 在仓库历史里）。版本不同也能试，见第八节。
3. Node `^22.19.0 || >=24`；pnpm（仓库 `packageManager` 声明 `pnpm@11.7.0`）。
4. **工作区干净**（安装脚本会拒绝未提交改动，可用 `--force` 绕过）。
5. 能联网执行 `pnpm install`。

## 四、安装

```sh
tar xzf dsh-access-management-0.1.5-rc.2.tar.gz
cd dsh-access-management-0.1.5-rc.2

# 先干跑一遍看基线检查：不装依赖也不构建
./install.sh --repo /path/to/deepseek-harness --no-install --no-build

# 确认无误后完整安装（git am 三个补丁 → pnpm install → pnpm run build）
./install.sh --repo /path/to/deepseek-harness
```

脚本依次做四件事，任一步失败都会明确报错退出：

1. 校验目标仓库（`package.json` 名称为 `@deepseek-ai/dsh-root`、git 仓库、工作区干净）与版本基线；
2. `git am --3way` 依次应用三个补丁（生成三个真实提交，便于日后跟随上游 rebase）；
3. `pnpm install`；
4. `pnpm run build`（整仓构建，视机器性能需要数分钟）。

安装记录写入 `<repo>/.git/dsh-access-management-install`（含安装前 commit SHA，供回滚使用）。

| 参数 | 作用 |
| --- | --- |
| `--repo <dir>` | 目标仓库路径（默认当前目录） |
| `--apply` | 只改工作区并暂存，不生成提交 |
| `--no-install` / `--no-build` | 跳过对应步骤 |
| `--force` | 允许脏工作区或对已安装过的仓库再执行 |

**装完必须重启 DSH 进程**才生效：

```sh
systemctl --user restart dsh-web     # 若目标机是用户级 systemd 服务
# 否则按目标机自己的方式重启 dsh web
```

## 五、安装后验证

```sh
./verify.sh --repo /path/to/deepseek-harness           # 静态自检：文件 / 名册 / tsconfig / 构建产物 / 安装记录
./verify.sh --repo /path/to/deepseek-harness --tests   # 再跑本功能相关的测试文件
```

静态自检应输出 `结果：通过 20，失败 0，警告 0`（未构建时构建产物会记 warning，不算失败）。

页面实测（重启后用启动日志里的 `?token=...` 链接打开）：

1. 设置 → **访问**，出现「登录令牌」「设备」两个列表；
2. 「新建令牌」输入设备名 → 拿到一次性登录链接；
3. 在另一台设备打开该链接 → 回到页面，该设备出现在设备列表（带浏览器、地址、时间）；
4. 点该设备「登出」→ 该设备下一次请求返回 401（刷新即被踢回登录）；「吊销」令牌 → 它签发的设备一并失效。

> **一次性影响**：升级前已建立的浏览器会话（v1 cookie）会被拒绝，现有浏览器需要用启动令牌**重新登录一次**。这是 0002 补丁的预期行为，不是故障。

## 六、回滚

```sh
./uninstall.sh --repo /path/to/deepseek-harness
```

脚本按**逆序** `git revert` 安装时生成的三个提交（栈式卸载，保证每一步 pre-image 与当前树一致），随后 `pnpm install && pnpm run build`，最后同样重启进程。回滚完成后工作区应干净、与安装前 commit 无差异。

若安装时用了 `--apply`（未生成提交），脚本会拒绝自动回滚并打印手工步骤；确认可以从安装前 SHA 硬重置时加 `--hard`。

## 七、注意事项

- **非 loopback 访问要加 `--trusted-host`**：`dsh web --trusted-host <域名或 IP>`，否则登录链接与 API 请求会被信任校验挡掉。
- **0003 补丁的语义**：改变的是「远端浏览器的设置文档是否落盘」，不影响认证与访问目录本身。
- 令牌 secret 与 cookie 签名密钥**明文**存放在 credential store，按该文件原有权限策略管理。
- 本包**不含**：两个纯视觉的侧边栏提交、nginx/证书配置——与访问管理无关，按目标机需要单独处理。
- 功能边界：设备列表里的设备属于「已签发 cookie 的浏览器」；会话 cookie 有效期 30 天，过期需重新用令牌链接登录。

## 八、故障排查

| 现象 | 处理 |
| --- | --- |
| 提示「目标版本 … 与打包基线不一致」 | 可继续：`git am --3way` 会做三方合并。若冲突，脚本自动 `git am --abort` 回到安装前状态并退出，此时改用 `overlay/` 手工覆盖（对照 `MANIFEST.md` 的 SHA-256 核对），或按提交 `3a054552` / `c88b4a2e` / `fc42f08a` 在新基线上 cherry-pick |
| 提示「工作区不干净」 | 先提交或贮藏改动；确要继续加 `--force` |
| 提示「看起来已安装过」 | 已装过；要重装先 `./uninstall.sh` |
| 日志出现「未配置 user.email，使用 dsh-local」 | 正常：脚本为本次提交使用固定身份，不影响功能；想用自己的身份先 `git config user.email <邮箱>` |
| `pnpm install` 失败 | 需要联网；若是 store 权限/只读问题，改用 `--no-install`，再由你手动在目标仓库执行 `pnpm install` |
| 重启后设置里没有「访问」 | 确认 `packages/client/ui-settings-access/lib/client.js` 已生成（说明 `pnpm run build` 跑完），再跑 `./verify.sh` 看哪项失败；浏览器强制刷新一次 |
| 页面能开但新建令牌报错 | 查 `dsh web` 进程日志；确认 `packages/api/remotes` 也已重新构建 |
